# Lingvo Connect CRM — Phase 09 Owner Patch 03
## ТЗ: архив заказов, настраиваемые архивные этапы и правки сетки

### 1. Цель патча
Закрыть обнаруженные владельцем MVP-регрессии до фиксации Release Candidate, не заходя в Phase 10 executor matching.

Ключевая проблема: заказ со статусом `Отменён` мог оставаться `archived=false`, поэтому исчезал из рабочего Kanban (где нет колонки `Отменён`) и одновременно не появлялся в `Архиве`.

### 2. Терминология
Чтобы не смешивать два уровня CRM:
- **воронка / board** — верхний контекст отображения заказов;
- **этап / status** — колонка внутри конкретной воронки.

В текущем патче фиксируются две системные воронки-контекста:
- `MAIN` — основная рабочая;
- `ARCHIVE` — архивная.

Полноценные произвольные именованные воронки уровня Bitrix24 (`МКО`, `МПП` и т.п.), каждая со своим набором этапов и отдельным переключателем, остаются следующим самостоятельным архитектурным расширением. Текущая модель MAIN/ARCHIVE должна быть для него фундаментом, а не тупиком.

### 3. Архив заказов
1. Системный статус `Отменён / CANCELLED` относится к `ARCHIVE`.
2. Все существующие заказы со статусом `CANCELLED` при миграции получают `archived=true`.
3. Основной Kanban и фильтр статусов показывают только этапы `MAIN`.
4. При включении `Архив` таблица, Kanban и фильтр статусов работают только с `ARCHIVE`.
5. В карточке активного заказа в меню `…` есть действие `Добавить в архив`.
6. Оно переводит заказ в архив и устанавливает стартовый архивный этап `Отменён`.
7. В архивной карточке доступно действие `Вернуть в основную воронку`; заказ возвращается в стартовый рабочий этап `Новый`.
8. Любое изменение статуса синхронизирует поле `archived` с принадлежностью статуса к MAIN/ARCHIVE.

### 4. Настраиваемые причины / этапы архива
Раздел `Настройки → Статусы заказов` расширяется, без отдельной новой админ-страницы.

Администратор может создать пользовательский этап и задать:
- название;
- воронку: `Основная` или `Архив`;
- цвет;
- порядок;
- доступность для выбора.

Примеры возможных архивных этапов: `Перенесён`, `Отложен`, и любые причины, которые решит использовать клиент. Эти примеры не создаются автоматически как фиктивные бизнес-данные.

Внутренний код пользователь вводить не должен — он генерируется backend автоматически.

Системные этапы сохраняют свою системную принадлежность к воронке. Например, `CANCELLED` нельзя случайно перенести обратно в MAIN через настройки. Пользовательские этапы можно распределять между MAIN и ARCHIVE.

### 5. Поведение архивного Kanban
- При первом архивировании заказ попадает в колонку `Отменён`.
- Если администратор добавил дополнительные архивные этапы, они появляются отдельными колонками архивного Kanban.
- Архивный заказ можно перенести на другой архивный этап.
- Архивные этапы не появляются в рабочей воронке и не раздувают обычный выбор статуса.

### 6. Финансы — правка сетки
На desktop карточка `Для клиента / Предварительный расчёт` должна начинаться по одной горизонтальной линии с карточкой `Итоговая стоимость заказа`.

Запрещён screenshot-specific отступ. Выравнивание реализуется структурой CSS Grid.

На tablet/mobile блоки могут естественно складываться в одну колонку.

### 7. Файлы заказа — правка сетки
На desktop одна строка файла должна сохранять в одной горизонтальной линии:
- PDF/file mark;
- имя файла и служебный текст;
- количество страниц;
- количество знаков;
- статус анализа;
- `Открыть` / `Скачать`.

Кнопки не должны проваливаться на новую вертикальную строку из-за увеличенного текста.

На узком экране допустим локальный горизонтальный scroll только внутри плотного списка файлов; document-level overflow запрещён.

### 8. Не входит в этот Phase 09 patch
- Phase 10 подбор исполнителей, availability и routing;
- редизайн знака `LC/` — зафиксирован для Phase 10 owner polish;
- полноценный конструктор произвольных именованных воронок с отдельным pipeline selector;
- личные кабинеты клиентов на основном сайте;
- регистрация, профиль, история заказов на сайте;
- website → CRM Orders интеграция;
- удаление/пересмотр раздела `Заявки`.

### 9. Будущая интеграция сайта
После MVP публичный сайт и CRM должны стать одной связанной системой. Целевой сценарий:
- клиент регистрируется на основном сайте;
- создаёт заказ;
- загружает файлы и указывает данные заказа;
- заказ напрямую создаётся в CRM `Заказы` со статусом `Новый`;
- далее в CRM работает Phase 10 matching исполнителей;
- клиент видит историю и состояние заказа в личном кабинете.

Раздел `Заявки` пока сохраняется для обратной совместимости и существующих источников лидов; решение о его упрощении/удалении принимается отдельно после подключения публичного сайта.

### 10. Acceptance criteria
- отменённый заказ больше не может потеряться между Table/Kanban/Archive;
- `Отменён` отображается в архивном Kanban;
- пользовательские архивные этапы создаются из Settings;
- цвета и порядок этапов сохраняются;
- MAIN и ARCHIVE не смешивают статусы;
- существующие CANCELLED заказы мигрируют в архив;
- Finance card выровнена с `Итоговая стоимость заказа`;
- кнопки файлов не проваливаются на второй ряд desktop;
- миграция non-destructive и имеет один Alembic head;
- предыдущие Phase 08/09 audits продолжают проходить;
- CSS debt (`!important`) не увеличивается.
