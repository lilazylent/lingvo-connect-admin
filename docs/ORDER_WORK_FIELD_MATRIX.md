# Матрица полей регистрации заказа — DOCX v3 (31.10.2026)

Источник: `ПРО_РАСПОЛОЖЕНИЕ_ЯЧЕЕК_версия_3_311026.docx` (20 таблиц: 1 общая, 16 видов работ, 3 макета оплаты).
Таблицы прочитаны из `word/document.xml` вместе с объединёнными ячейками (`gridSpan` / `vMerge`), а не из плоского текста.
Платный пакет доработок, мастер-промпт от 31.10.2026.

Легенда Олега: РС — раскрывающийся список, П — переключатель из двух вариантов (левый по умолчанию), Г — галочка,
З — вручную, А — автоматически, но можно исправить вручную.

Сетка работы — 4 колонки. Запись `поле×2` означает ячейку на две колонки. Канонический владелец раскладки —
`SERVICE_DEFINITIONS[...]["layout"]` в `apps/api/app/service_definitions.py`. Фронтенд рендерит строки как есть,
16 копий формы нет.

## 01 · Общее и Клиент (таблица 1)

| Строка | Колонка 1 | Колонка 2 | Колонка 3 |
|---|---|---|---|
| 1 | Номер заказа (А) — `orders.number`, автонумерация `YY-NNNN`, можно исправить | Дата заказа (А) — `orders.created_at`, по умолчанию сегодня; при редактировании не подменяется | Статус (РС) — `orders.status`, по умолчанию `NEW` «Новый» |
| 2 | Клиент (РС) — `orders.client_id` | Контактное лицо (РС) — `orders.contact_id`, только контакты выбранного клиента | Ответственный (А/РС) — `orders.manager_id`, по умолчанию текущий сотрудник **только для нового заказа** |
| 3 | Дата окончания (З/календарь) — `orders.deadline` + `orders.deadline_manual` | Время окончания (РС/З) — `orders.deadline_time_mode` = `DURING_DAY` (по умолчанию) / `BY` / `EXACT` + `orders.deadline_time` HH:MM | Комментарий (З) — `orders.notes` |

Миграция `0029_paid_package_v3`: новые колонки nullable или с безопасным default. У старых заказов
`deadline_time_mode = ''` («не указано»), `deadline_manual = false`: срок, как и раньше, вычисляется по максимальному сроку работ.
Старые сроки не теряются. Заданная вручную дата окончания заказа (`deadline_manual = true`) больше не перезаписывается
пересчётом работ. Работы без своего срока получают срок заказа при создании.

Сводка в шапке мастера (справа от «Регистрация заказа», не sidebar): номер (для нового заказа — с пометкой «предв.»,
до создания номер не резервируется), дата, клиент, контакт, срок + время, статус. Значения берутся из того же state
первого шага, второго state нет.

## 02 · Работы (таблицы 2–17)

Общие блоки (одинаковые места во всех текстовых услугах):

- **R-мод** «Наценка / Срочность (З)», коэффициент по умолчанию 1 → `urgency_multiplier`; `urgent = multiplier > 1`.

### Сроки работы

В таблицах работ v3 срока нет: срок задаётся на уровне заказа. Старые и новые работы сохраняют `deadline`,
`deadline_time`, `start_date`, `start_time` (подбор исполнителя и календарь используют срок работы). В форме эти поля
убраны в свёрнутый блок «Срок работы, если отличается от срока заказа». Скрытые поля при сохранении не очищаются.

## Решения по конфликтам v3 ↔ текущая модель

1. **Полный / повторения / шаблон.** Это не три отдельные услуги и не независимый переключатель. Это одна услуга
   `written_translation` с вариантами `CHARACTERS` / `REPETITIONS` / `DOCUMENT` (`certification_mode`). В списке «Услуга»
   они показаны тремя пунктами с названиями Олега, отдельного селектора «Способ расчёта» нет. Старые работы с `DOCUMENT`
   и `CHARACTERS` открываются без миграции.
2. **Повторения −30 %.** Тариф полного перевода (включая тариф клиента для варианта `CHARACTERS`), а автоматическая
   скидка = 30 % вместо скидки от объёма или скидки клиента. Порядок: ставка × объём × наценка → −30 %.
   Ручная скидка **заменяет** автоматическую 30 %, а не добавляется к ней. Двойного применения нет.
3. **Вычитка = тариф полного перевода − 30 %.** Подбирается тариф письменного перевода (то же направление, носитель,
   через русский), ставка = тариф × 0,7 (до копеек). Скидка от объёма применяется к уже уменьшенной ставке, как у
   обычного тарифа. Своих тарифов у вычитки в базе нет; тарифы клиента для вычитки, если их заведут, имеют приоритет.
4. **«Редактура» (`editing`).** По словам Олега, «повторения» — «то, что было Редактура». Старые работы «Редактура»
   не переименовываются и не пересчитываются. Отключить услугу для новых работ можно в «Настройки → Услуги»;
   это решение владельца, кодом услугу не отключаем.
5. **Устный перевод.** Две услуги в базе (тарифы и исполнители привязаны к коду) остаются. В форме одна позиция
   «Устный перевод» и переключатель «Тип перевода: Последовательный / Синхронный», который меняет `service_code`.
   Исторические работы и тарифы не мигрируются.
6. **Тематика (РС).** Новый справочник `topic_catalog` (31 значение, идемпотентный seed). `order_works.topic` хранит
   название, как раньше. Старое значение вне справочника показывается в списке как «(не из справочника)» и не теряется.
7. **Номер и дата счёта.** Структурированные `client_payments.invoice_number` / `invoice_date` не удаляются и не
   переносятся. Блок свёрнут в «Реквизиты счёта». Несколько счетов по частям пишутся в комментарии оплаты, как просил
   Олег; полноценный учёт нескольких счетов — отдельное расширение.

## 03 · Расчёт — макеты оплаты (таблицы 18–20)

Одно финансовое состояние (`client_payments` + `finance()` + журнал депозита), меняется только представление:

| Способ | Строка 1 | Строка 2 |
|---|---|---|
| Не выбран / Наличные / Безналичный | Способ оплаты · Стоимость заказа, р. (А) · Оплачено, р. (З) · Осталось к оплате, р. (А) | Дата оплаты×2 · Комментарий×2 |
| Депозит | Способ оплаты · Стоимость заказа, р. · Депозит, р. (А: списано по журналу) · Осталось к оплате, р. | Дата оплаты×2 · Комментарий×2 |

«Депозит» — сумма `ClientDepositTransaction(kind=ORDER_DEBIT)` по заказу. Перерисовка ничего не списывает.
Списание остаётся только в существующем месте: создание заказа.

## Клиент и исполнитель: минимум

Клиент: правило 1 условной страницы сохраняется (`conditional_page_quantity(..., minimum=True)`).
Исполнитель: объём считается без клиентского минимума (0,1 страницы допустимо), округление вверх до 0,1 не меняется.
В таблице Олега «Заказы 2026» страницы исполнителя округлены до 0,01 (205032 знака → 113,91). Это вопрос к владельцу,
правило округления не меняли.
