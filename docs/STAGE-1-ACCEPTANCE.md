## Что завершено

- Добавлен совместимый multipart endpoint публичной формы с одним вложением.
- Вложение проверяется по размеру, расширению и фактической сигнатуре/структуре файла.
- Пустые, исполняемые, повреждённые и неподдерживаемые файлы отклоняются.
- Файл сохраняется вне публичного web-root и скачивается только после авторизации сотрудника.
- Публичный файл показывается в карточке с подписью «Прикрепил клиент на сайте».
- Создание заявки и metadata файла выполняется одной транзакцией; ошибка базы удаляет сохранённый файл.
- Идемпотентный повтор не создаёт вторую заявку или второй файл; тот же ключ с другими данными возвращает конфликт.
- В activity добавлено отдельное событие `public_file_attached` без персональных данных и содержимого файла.
- Добавлена миграция nullable uploader для файлов публичной формы; идентификатор совместим с уже применённой локальной ревизией.
- В очередь заявок добавлены язык, диапазон желаемого срока, отображение срока и сортировка по сроку.
- В UI пользователей добавлено редактирование имени и роли; сервер по-прежнему запрещает снять права с собственной ADMIN-учётной записи.
- Добавлен тест редактирования/деактивации пользователя и отзыва его активных сессий.
- Документация приведена в соответствие с фактическим JSON/multipart контрактом.
- Backend lint приведён к зелёному состоянию на чистой версии Этапа 1.

## Проверенные сценарии

1. Неавторизованный пользователь не открывает административные API и файл заявки.
2. Первый вход требует сменить временный пароль, затем подключить 2FA.
3. Корректный TOTP с допустимым небольшим рассогласованием времени принимается.
4. Recovery-код работает только один раз; logout завершает сессию.
5. ADMIN создаёт, редактирует, деактивирует сотрудника и сбрасывает пароль/2FA.
6. MANAGER работает с заявками, но получает `403` на users/settings/tariffs.
7. Заявка без файла поступает с сайта и не дублируется при повторе.
8. Заявка с PDF поступает с сайта, файл виден в карточке и доступен только сотруднику.
9. Небезопасный файл отклоняется, пустая заявка в базе не остаётся.
10. Ручная заявка создаётся, находится поиском и фильтрами, сортируется и открывается.
11. Менеджер, языки, желаемая дата, внутреннее резюме и статус сохраняются.
12. Комментарии и внутренние файлы появляются в карточке и журнале.
13. Конфликт параллельного редактирования возвращает понятный `409`.
14. Dashboard показывает реальные количества и последние заявки.
15. Desktop/tablet/mobile макеты не имеют горизонтального переполнения; dropdown поддерживает mouse и keyboard.

## Граница Этапа 1

В Этап 1 не включались Clients, Orders, Translators, Finance, CMS, интеграции, сложный RBAC и расширенная аналитика. Незавершённые локальные файлы будущего раздела Clients не добавлялись в коммиты Этапа 1.

## Перед production-публикацией

- создать или подключить отдельный приватный GitHub-репозиторий админки;
- задать production secrets вне Git и включить `COOKIE_SECURE=true`;
- указать публичному сайту production URL единственного Applications API;
- разрешить CORS только для production-доменов сайта и админки;
- обеспечить HTTPS, резервное копирование PostgreSQL и постоянного файлового volume/object storage;
- исправить локальную настройку Docker HTTPS proxy, если образы требуется собирать на этом компьютере.

Кодовая часть Этапа 1 завершена. Production deployment не считается выполненным до подключения repository/hosting и production secrets.
