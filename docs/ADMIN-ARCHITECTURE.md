# Архитектура Lingvo Connect Admin

## 1. Статус документа

Это целевая архитектура для будущей реализации. На Phase 0 прикладной код, авторизация и интеграция не создаются.

## 2. Архитектурное решение

Система строится как отдельный модульный монолит:

- `apps/admin-web` — Next.js, React, TypeScript;
- `apps/api` — FastAPI, Python;
- PostgreSQL — единственное постоянное хранилище бизнес-данных;
- Docker Compose — локальная среда разработки;
- OpenAPI — контракт между frontend, backend и публичным сайтом.

Frontend не обращается к базе напрямую. Все изменения проходят через FastAPI, где выполняются авторизация, проверка роли, валидация, аудит и транзакции.

## 3. Границы модулей backend

| Модуль | Ответственность |
|---|---|
| `auth` | пользователи, роли, сессии, вход и выход |
| `applications` | заявки с публичного сайта, назначение ответственного, конвертация |
| `customers` | компании и контактные лица |
| `orders` | заказы, позиции услуг, сроки, статусы |
| `catalog` | услуги, языки, статусы, тарифы и их версии |
| `workforce` | исполнители, языковые пары, назначения |
| `files` | метаданные файлов и выдача прав на загрузку/скачивание |
| `collaboration` | комментарии и внутренние заметки |
| `audit` | неизменяемый журнал действий |
| `reporting` | агрегаты для операционного дашборда |

Модули имеют общий процесс развертывания, но не должны обходить сервисные границы произвольными запросами к чужим таблицам.

## 4. Frontend

- App Router и строгий TypeScript.
- Server Components используются для оболочки и первичного чтения, Client Components — только для интерактивности.
- Типизированный API-клиент генерируется из OpenAPI; ручные дублирующие типы не являются источником истины.
- Доступ к страницам проверяется и на уровне маршрута, и повторно на API.
- Таблицы используют серверную пагинацию, сортировку и фильтры.
- Ошибки API переводятся в понятные состояния формы; optimistic update допустим только там, где предусмотрен безопасный откат.

## 5. Backend и данные

- Python 3.12+, FastAPI, SQLAlchemy 2, Alembic, Pydantic 2.
- PostgreSQL 17 является единственным владельцем актуального состояния.
- UUID применяются как внешние идентификаторы; человекочитаемый номер заказа формируется отдельной последовательностью.
- Денежные значения хранятся в `numeric`, а не `float`.
- Важные изменения выполняются в одной транзакции вместе с записью аудита.
- Удаление рабочих сущностей заменяется архивированием, если закон не требует физического удаления.

## 6. Авторизация и роли

Планируется локальная учетная запись с паролем и непрозрачной серверной сессией.

- Пароли: Argon2id.
- В браузере: `HttpOnly`, `Secure`, `SameSite=Lax` cookie.
- В базе хранится только хеш токена сессии.
- После входа идентификатор сессии ротируется; действуют абсолютный и неактивный таймауты.
- Небезопасные методы защищаются проверкой `Origin`/`Referer` и CSRF-токеном, если схема размещения потребует cross-site сценария.
- Вход ограничивается по частоте; ошибки не раскрывают существование пользователя.

Начальные роли:

- `admin` — управление пользователями, справочниками и всеми рабочими данными;
- `manager` — работа с заявками, клиентами, заказами и исполнителями в пределах согласованных прав.

Точная матрица прав, особенно доступ менеджера к финансовым данным, требует подтверждения клиента.

## 7. Файлы

Файлы не хранятся BLOB-ами в PostgreSQL. В базе находятся метаданные, контрольная сумма и ключ объекта. Локально допустим S3-совместимый storage-контейнер; производственный провайдер выбирается отдельно.

Требования к будущей реализации:

- приватные объекты без публичных URL;
- короткоживущая авторизация скачивания;
- проверка MIME, расширения и размера;
- статус антивирусной проверки до выдачи файла;
- журнал загрузок и скачиваний;
- политика хранения и удаления после согласования.

Публичная форма передаёт вложение через отдельный multipart endpoint. Файл проходит серверную проверку формата и лимита, хранится вне web-root и доступен только из авторизованной карточки заявки.

## 8. Интеграция с публичным сайтом

Текущий публичный контракт `POST /api/public/leads` сохраняется совместимым. Целевая схема не допускает двух независимых писателей в одну бизнес-модель.

План переключения:

1. Реализовать совместимый endpoint в новом API и контрактные тесты.
2. Выполнить пробную миграцию существующих заявок в тестовой среде.
3. На короткое окно остановить запись в старый backend.
4. Перенести данные и проверить количество, идентификаторы и временные метки.
5. Переключить публичный сайт на новый URL API.
6. Выполнить тестовую заявку и сверить ее в админ-панели.
7. Сохранить возможность отката URL до окончания приемки.

До отдельного разрешения ни публичный репозиторий, ни его переменные окружения не изменяются.

## 9. Наблюдаемость и безопасность

- структурированные логи без персональных данных и содержимого документов;
- request/correlation ID через публичный запрос, API и аудит;
- health/readiness endpoints без секретов;
- резервные копии PostgreSQL и storage с проверяемым восстановлением;
- зависимости и контейнеры фиксируются по версиям и проверяются на уязвимости;
- секреты поступают только из окружения/секрет-хранилища и не коммитятся.

## 10. Изоляция репозиториев

Админ-панель не импортирует исходники из `lingvo-connect` и не использует относительные пути к нему. Общая граница — опубликованный HTTP/OpenAPI-контракт и явно запускаемые скрипты миграции данных. Это позволяет версионировать и развертывать оба приложения независимо.

## 11. Отложенные решения

- производственный хостинг и домены;
- поставщик объектного хранилища;
- SMTP/уведомления;
- внешняя identity-система или 2FA;
- точные формулы тарификации;
- политика хранения персональных данных и файлов.

Они перечислены в [OPEN-QUESTIONS.md](./OPEN-QUESTIONS.md) и не должны быть угаданы в коде.
