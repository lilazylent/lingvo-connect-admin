2. ШАГ «РАСЧЁТ» — ТАРИФ / СТАВКА / РУЧНОЙ ИТОГ / АВТОРАСЧЁТ
==================================================

Сейчас в карточке работы, например:

«1. Письменный перевод»

в одной горизонтальной строке расположены:

- Тариф
- Ставка по тарифу
- Ручной итог
- Авторасчёт

Проблема:

поле «Тариф» содержит длинное значение:

«Русский → Английский · 2200 ₽ · Усл. страница / 1800 знаков · рекомендован»

и визуально конфликтует с соседним блоком «Ставка по тарифу».

Создаётся ощущение, что один элемент залезает на другой.

Нужно полностью исправить геометрию этой строки.

ТРЕБОВАНИЯ:

- каждый из четырёх элементов должен иметь строго свою колонку;
- элементы не должны пересекаться или визуально накладываться;
- поле «Тариф» может быть шире остальных;
- «Ставка по тарифу»;
- «Ручной итог»;
- «Авторасчёт»

должны находиться на одном вертикальном и горизонтальном уровне;

- у соседних карточек должна быть согласованная высота;
- верхние границы должны совпадать;
- нижние границы должны совпадать;
- label'ы должны находиться на одинаковой высоте;
- внутренние padding должны быть визуально согласованы;
- длинное значение тарифа не должно растягивать grid;
- использовать min-width: 0 там, где это необходимо;
- закрытое значение тарифа при нехватке места должно корректно обрезаться через ellipsis;
- не переносить длинное название тарифа хаотично на несколько строк, если из-за этого ломается высота всей строки;
- полную информацию о тарифе можно оставить внутри раскрытого dropdown;
- dropdown при открытии не должен быть искусственно узким, если там требуется показать полное описание;
- проверить поведение на desktop и при уменьшении ширины окна.

Сетка должна ощущаться аккуратной и профессиональной.

Ориентир:

[ ТАРИФ — самая широкая колонка ]
[ СТАВКА ]
[ РУЧНОЙ ИТОГ ]
[ АВТОРАСЧЁТ ]

Никаких overlap / overflow между колонками.

4. ПОВТОРЯЮЩИЕСЯ UI-ЭЛЕМЕНТЫ ДОЛЖНЫ БЫТЬ ОДИНАКОВЫМИ
==================================================

В проекте сейчас встречается проблема:

одинаковые по смыслу controls на разных страницах визуально отличаются.

Конкретный пример:

кнопка / control «Архив»

на страницах:

- Клиенты;
- Исполнители;
- Заказы

имеет разную форму.

Где-то она более округлая / овальная.
Где-то более прямоугольная.

Так быть не должно.

ПРАВИЛО:

одинаковый смысл элемента → одинаковый UI-паттерн.

Для одинаковых controls должны совпадать:

- высота;
- border-radius;
- border;
- padding;
- font-size;
- font-weight;
- line-height;
- цвет;
- background;
- hover;
- focus;
- active;
- disabled;
- расположение иконки;
- расстояние между иконкой и текстом;
- визуальная плотность.

Выбрать один общий стиль для «Архив».

Предпочтительно:

современный SaaS-style,
умеренно скруглённый прямоугольник,
НЕ сильный pill / капсула.

Применить одинаковый вариант во всех местах, где используется аналогичный control.

5. ОБЩЕЕ ПРАВИЛО ДИЗАЙН-СИСТЕМЫ
==================================================

Перед созданием нового CSS-класса или UI-паттерна:

проверить, существует ли уже аналогичный control.

Если существует —
использовать общий класс / компонент / design token.

Не создавать:

archive-button-clients
archive-button-orders
archive-button-contractors

если это визуально один и тот же control.

Предпочтительно использовать:

- общий компонент;
или
- общий CSS-класс;
или
- единый набор design tokens.

6. FRONTEND CONSISTENCY PASS
==================================================

Проведи аккуратный аудит существующих страниц CRM.

Не переделывай интерфейс с нуля.

Проверь:

- input;
- select;
- combobox;
- textarea;
- toggle;
- checkbox-like controls;
- secondary buttons;
- filters;
- archive controls;
- cards;
- toolbar controls.

Особенно:

- одинаковые ли у них базовые высоты;
- одинаковые ли radius у одинаковых типов;
- не прыгают ли элементы по вертикали;
- нет ли случайных padding;
- нет ли элементов, стоящих на 3–8 px выше/ниже соседних;
- не ломается ли grid от длинного текста;
- не вылезает ли содержимое за рамки;
- кликабельна ли вся ожидаемая область control;
- нормальные ли hover/focus состояния;
- одинаково ли выглядят одинаковые элементы на разных страницах.

==================================================
7. ВАЖНОЕ ПРАВИЛО ДЛЯ GRID / FLEX
==================================================

При работе с grid/flex внимательно учитывать длинный текст.

Для grid children, где есть text overflow:

- использовать min-width: 0;
- использовать overflow: hidden при необходимости;
- text-overflow: ellipsis;
- white-space: nowrap там, где перенос разрушает строку.

Не допускать ситуации:

длинный текст в первой колонке расширяет колонку и физически залезает на вторую.
